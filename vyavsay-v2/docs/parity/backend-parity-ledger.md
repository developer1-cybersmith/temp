# Backend parity ledger

**Summary**
1. One row per legacy route, service, job, integration, SQL rule and frontend-relied behaviour: 195 rows (59 routes incl. 4 frontend-only, 43 services, 6 jobs, 36 integrations, 23 SQL rules, 28 behaviours). Generated from [07-backend-migration-plan](../07-backend-migration-plan.md); edit status cells by hand, regenerate nothing else.
2. A row is DONE only when every applicable status cell is `done` (rules in "How to use" below). The linter story P0.4 fails CI when a route, an FE call pattern or a `@parity(id)` marker is missing here, or when a fixture's `legacy_ref` does not resolve or its `signed_by` is empty or equals `derived_by`.
3. Status values: `todo`, `wip`, `done`, `n/a` (not applicable, e.g. drops have no fixture), `parked` (needs the DB; set to `todo` when DB work resumes, story P5.2).
4. Legacy refs are `path:line` relative to `backend/src/`, except `database/...` (relative to `backend/`; bare `NNN-name.sql` refs are in `backend/database/migrations/`) and `frontend X.tsx` (relative to `frontend/src/`). Nothing was run.
5. Intentional deviations are not rows here; they are `CHG-nn` in plan section 5 and are cited in Notes.

## How to use
| Column | Meaning | Done when |
|---|---|---|
| Fixture | Golden request/response or golden table exists, with `legacy_ref`, `derived_by`, `signed_by`, trust level L1 (read from code), L1s (second reader signed), L2 (every key the page reads is present and the FE response type is covered), L3 (owner saw it in the UI, or it matches a captured legacy response) | File committed; L2 for FE-called routes; L3 for rows with a visible CHG and for rows whose Notes say `Capture L3` |
| 2nd | A different reader derived the expected response from the cited legacy line without seeing the fixture, diffed, and signed (plan 2g) | `signed_by` set and differs from `derived_by` |
| Red | The test was merged failing before the code | Commit order shows test first |
| Green | Passes on memory repos and fakes in CI (Gm). Gm is not RLS proof and does not close M2 or M3 (plan 2e) | Required check green |
| FE | The frontend read-set check passed (every key the caller reads, page by page) | `tests/contract/fe_reads` check green |
| PG | Same test passes on Postgres (Gp); closes M2 and M3. It is a test re-run, not a dual run of legacy | Set when DB work resumes (P5.2) |
| Test | C contract, L cross-tenant leak probe, G golden table, B behaviour scenario, F fault or concurrency, K conformance, S typed stub, A absence (dropped item stays gone), E eval (agent plan) | |
| Touchpoint rows T01..T44 (story P3.18, [09 s5](../09-agent-backend-sync-contract.md)) | Test cell holds exactly one of: a seam scenario id, `A:<check>` (absence, for dropped items), or `n/a(reason, revival story or none)` | The linter fails a T row with none of the three |
